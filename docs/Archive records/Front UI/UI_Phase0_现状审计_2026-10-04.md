# HD2Mimnt Phase 0：UI 现状审计

**审计日期：** 2026-10-04  
**审计范围：** `src/HD2Mimnt.UI`、UI 直接依赖的 Application/Infrastructure 注册、`tests/HD2Mimnt.Tests` 中的 UI 相关测试，以及现有 UI 计划和报告。  
**审计目标：** 建立后续 UI 设计与开发的事实基线，确认现有实现、可复用能力、缺口和验收边界。  
**结论性质：** 代码与命令证据审计，不等同于完整人工视觉验收。

## 1. 执行摘要

当前 UI 是一个基于 Avalonia 12、.NET 10 和 CommunityToolkit.Mvvm 的桌面应用。主窗口提供四个一级入口：模组库、配置文件、设置、更多；任务中心和通知以主窗口覆盖层打开。页面通过 ViewModel 调用 Application 服务，数据库、部署和文件操作由 Infrastructure/Application 层提供，未发现页面直接创建 SQLite 查询或直接执行部署复制的主路径。

当前状态可以支持继续迭代，但还不适合宣称“UI 最终验收完成”。主要原因是：

- 一级导航使用隐藏 `TabControl`，页面生命周期和导航逻辑集中在 `MainWindowViewModel`，扩展成本较高。
- “更多”页面把插件、备份、日志、外部工具、性能说明集中纵向展示，信息层级和入口可发现性仍需重新整理。
- XAML 中存在较多直接写入的中英文 UI 文案；插件管理页面仍有英文界面文本，尚未形成统一本地化边界。
- 少量 View 仍使用 code-behind 点击事件，UI 操作边界尚未完全收敛到命令和 ViewModel。
- 全量测试本次未取得稳定的最终摘要，命令退出码为 1；ViewModel 过滤测试明确通过 44/44，因此不能把全量结果记录为通过，也不能据此判定 UI 失败。
- 高 DPI、长时间空闲、10,000+ 模组真实窗口滚动、窗口级交互和恢复流程仍需要人工验收。

## 3. 主窗口与导航现状

### 3.1 布局

`MainWindow.axaml` 使用三行布局：

1. 顶部导航栏：应用标题、四个导航 RadioButton、游戏状态、任务中心、通知、开发工具和版本。
2. 中间内容区：隐藏 TabItem 承载 `LibraryView`、`ProfileView`、`SettingsView`、`MoreView`。
3. 底部状态栏：当前配置文件、部署状态、任务状态。

窗口默认尺寸为 1280×800，最小尺寸为 960×600。任务中心和通知面板通过中间内容区上的半透明 Border 覆盖显示，并由 Escape 关闭。

### 3.2 导航行为

导航命令位于 `MainWindowViewModel`，通过 `SelectedTabIndex` 切换页面，同时维护 `CurrentView`。启动时一次性注入并创建主要页面 ViewModel；初始化过程依次加载库、配置、设置、任务、外部工具、插件、备份和日志。

现状优点：

- 一级入口明显，Ctrl+1 至 Ctrl+4 有快捷键。
- 任务和通知可以从全局位置进入。
- 页面切换不依赖页面内直接访问数据库。

现状风险：

- `CurrentView` 与隐藏 `TabControl` 同时存在，存在状态表达重复，后续新增路由需要同时维护多处逻辑。
- 主窗口构造函数依赖多个页面 ViewModel 和业务服务，职责偏重。
- 主要 ViewModel 在启动阶段全部初始化，页面首次进入速度和空闲资源占用需要实测确认。

## 4. 页面与功能覆盖

| 页面/区域 | 当前能力 | 当前边界 |
|---|---|---|
| 模组库 | 搜索、筛选、排序、选择、批量启用/禁用、导入、部署、清理、详情 | 冲突筛选没有可靠后端结果时不应伪造；大数据窗口滚动仍需人工验收 |
| 配置文件 | 配置列表、搜索、创建/删除/切换、模组启用状态、配置对比 | 需要继续验证切换期间取消、失败反馈和真实窗口状态同步 |
| 设置 | 游戏路径、部署方式、库默认排序/筛选、主题、列表密度、缓存操作 | 文案和分类仍是硬编码；设置保存后的全局反馈需要统一 |
| 任务中心 | 任务列表、进度、取消、失败重试入口 | 全局覆盖层尺寸固定，窄窗口和大量任务的体验未人工确认 |
| 更多 | 开发工具、插件、备份、日志、外部工具、关于、性能说明 | 内容过度聚合；部分插件页面为英文；外部工具存在事件处理 code-behind |
| 通知面板 | 未读计数、通知列表、导航到目标页面 | 需要人工验证遮罩、焦点、Escape 和重复打开行为 |
| 插件权限对话框 | 权限预览、授予/拒绝、管理 | 业务边界主要在服务中，但 UI 文案和异常反馈需统一 |

## 5. View 与 ViewModel 结构

当前主要 View 与 ViewModel 对应关系如下：

| View | ViewModel/数据上下文 | 备注 |
|---|---|---|
| `LibraryView` | `LibraryViewModel` | 核心模组库；包含较多批量操作 |
| `ProfileView` | `ProfileViewModel` | 配置列表、详情和对比区域 |
| `SettingsView` | `SettingsViewModel` | 按分类显示设置区块 |
| `TaskCenterView` | `TaskCenterViewModel` | 列表和取消命令 |
| `PluginManagementView` | `PluginManagementViewModel` | 插件管理和执行历史 |
| `BackupView` | `BackupViewModel` | 备份、恢复、删除 |
| `LogView` | `LogViewModel` | 刷新、复制、导出 |
| `MoreView` | `MainWindowViewModel` | 组合多个子 ViewModel |
| `DevToolsWindow` | `DevToolsViewModel` | 独立开发工具窗口 |
| `PluginPermissionDialog` | `PluginPermissionDialogViewModel` | 权限确认对话框 |

已发现的结构性问题：

- `MoreView` 直接承载多个完整功能模块，导致页面过长、入口层级不清。
- `MoreView` 的外部工具“启动”使用 `Click="OnLaunchToolClicked"`，说明该功能仍有 View 层事件处理。
- `LibraryView` 和 `MoreView` 也存在 code-behind 文件；需要逐个确认是否仅负责窗口/文件选择等 UI 桥接，避免把业务逻辑留在 View。
- 页面大量直接写入 `Text`、`Content` 和 `ToolTip.Tip`，当前没有统一资源键/本地化服务边界。

## 6. 服务边界与数据流

`App.axaml.cs` 中的 DI 注册显示 UI 通过以下层次连接业务：

```text
Avalonia View
    -> UI ViewModel
        -> Application Service
            -> Infrastructure Repository / Deployment / SQLite
```

已确认的主要服务：

- 模组：`ModService`、`SearchService`、`IModRepository`
- 配置：`ProfileService`、`IProfileRepository`
- 部署：`DeploymentService`、`IDeploymentRepository`、Copy/SymbolicLink/HardLink 方法
- 任务：`TaskService`、Import/Scan/Validation Worker
- 设置和游戏识别：`SettingsService`、`GameDetectionService`
- 插件、备份、日志、图片缓存和通知：对应 Application/Infrastructure 服务

边界结论：

- 当前主流程符合“UI 通过 Application 服务访问业务”的要求。
- UI 层没有把 SQLite 查询、部署复制或文件追踪逻辑直接写入 XAML。
- 后续改造必须继续保留该边界，尤其不要在 View 或 ViewModel 中补写 Repository 细节。

## 7. 列表、异步和取消现状

代码中已经使用 `ObservableCollection`、后台计算和取消令牌处理若干高频操作。现有文档和实现显示：模组筛选/排序在后台计算普通集合后回到 UI 上下文替换集合；配置详情读取已使用按 ID 查询以避免逐项读取；部署目录枚举放入后台任务并支持取消。

需要继续关注：

- 页面初始化阶段的多个异步加载目前由主窗口集中触发，应记录单项耗时和失败归属。
- `async void` 事件处理适合 UI 事件，但需要确保异常被捕获并反馈给通知系统。
- 大列表使用虚拟化的范围应以实际 XAML 为准逐页确认；`ItemsControl` 的大型列表不能默认视为已虚拟化。
- UI 线程集合替换、选中状态和批量命令需要继续保持串行和可取消。

## 8. 本地化与文案审计

当前 XAML 同时出现中文和英文文案。例如插件管理页面包含 `Plugin Management`、`Install Plugin`、`Loading...` 等英文文本，而主页面、配置页和设置页主要使用中文。现状说明：

- 尚未形成统一的中文资源键管理。
- 界面语言不一致，会增加后续视觉和验收成本。
- 硬编码文案会让错误提示、按钮语义和可访问性文本难以统一维护。

Phase 0 不直接迁移全部文案，但后续 UI 阶段应先建立资源键清单，再改页面，避免新增更多硬编码字符串。

## 11. 缺失接口与需要重构的组件清单

### 11.1 缺失或待确认的能力

1. UI 级统一本地化资源和语言切换边界。
2. 全局导航状态的单一来源，避免 `CurrentView` 与 `SelectedTabIndex` 重复表示。
3. 面向页面的加载/错误/空状态规范。
4. 可重复的窗口级高 DPI、窄窗口、键盘焦点和遮罩验收脚本。
5. 全量测试退出码 1 的可复现原因和分类日志。

### 11.2 优先重构组件

1. `MoreView`：拆分为清晰入口或独立页面，降低纵向聚合。
2. `MainWindowViewModel`：将页面导航、启动编排和全局状态分离。
3. `PluginManagementView`：统一中文资源和操作状态文本。
4. `LibraryView` / `MoreView` code-behind：只保留必要的 UI 桥接，业务动作回收到命令/服务。
5. 全局状态栏和通知：统一状态枚举、颜色、文案和失败反馈。
