# 1 万模组、配图与大量 SQL 联合性能测试

2026-10-17，当前工作区，Release / x64。结论：**当前不能认定在该规模下全程流畅**。虚拟化有效，关闭自动检查时稳定滚动期间输入队列响应较好，但初始化、配置刷新、全选有明显停顿，图片解码内存成本很高。自动检查开启后，滚动期间也出现明显抖动，详见[补充对照](#补充自动检查冲突的联合场景)。本轮仅补充测试和报告，未修改生产实现。

## 环境与样本

- Intel Core i5-12400F，31.9 GiB 内存，Windows 10.0.26300，.NET SDK 10.0.401 / Runtime 10.0.12。
- 真实磁盘 SQLite / WAL，10,000 个模组、12 个配置、21,000 条成员关系；当前配置包含全部 10,000 个模组。
- 每个模组有独立目录、名称、作者、标签、资源类型及描述。目录没有游戏数据正文，Workflow 为 Legacy，清单、来源 sidecar 缺失；这是受支持的旧格式路径，会包含目录检查、清单回填探测及 sidecar 不存在的开销。不能外推为所有带完整 manifest 的包都同样慢。
- UI 样本有 10,000 个独立 PNG 文件路径，每张 256 × 256，使用固定种子的噪声图片。内容来自同一模板，避免不同图片复杂度成为变量；路径缓存无法合并这些文件，实际经过 Skia 解码。不是原图大尺寸压力测试。
- 通过实际 DI、MainWindow、ViewModel、Application 服务和 Repository 操作。Headless 使用 Skia 实际绘制，窗口为 1280 × 830。
- 服务测试每项 7 次，记录首轮及后 6 次的分布；UI 场景一次完整运行，每页 180 次滚轮输入并截图，检查末项可达及已实现容器数量。
- UI 测试持续约 112 秒；其中 SQL 负载约 91.35 秒，从初始化前持续到操作、刷新和稳定等待完成。4 个工作线程各用独立连接，约 85% 主键查询、5% 分类计数、5% FTS 计数、5% `UPDATE Size=Size`。更新保留原值，但仍执行写语句、事务与现有触发器。应用本身继续使用现有 Repository 连接，没有并发复用单一 SqliteConnection。
- 数据生成不计入操作耗时；新建图片受系统文件缓存影响，首次解码不等于物理磁盘冷读取。测试不操作真实用户库或游戏目录。

| 初始化期间最长输入调度延迟 | **24.40 秒** |
| 模组库搜索 Armor，命中 5,000 项并布局 | 524.96 ms |
| 模组库搜索单项 / 无结果 / 清空 | 16.62 / 8.02 / 38.27 ms |
| 模组库降序排序 | 32.46 ms |

| 配置页搜索 Armor / 单项 / 无结果 / 清空 | 40.31 / 26.55 / 3.57 / 37.09 ms |

输入探针从后台线程每约 16 ms 向 UI Dispatcher 的 Input 优先级投递，记录入队至执行的延迟；每次收到回调后才发下一个。它能看到长时间停顿，但不能把一次 24 秒冻结当作 1,500 个独立采样。全场 P95 只有 3.57 ms，**不能用这个聚合值掩盖最长 24.40 秒的冻结**。配置刷新时探针也测到 6.56 秒延迟；全选/清空操作的延迟与操作耗时一致。

| 滚动场景 | 单次输入 + 布局 + 截图 P50 / P95 / 最大 | 输入探针 P95 / 最大 | 最大实现容器数 |
| --- | --- | --- | ---: |
| 模组库，180 次 | 19.93 / 39.90 / 79.25 ms | 5.24 / 33.21 ms | 8 |
| 配置页，180 次 | 21.84 / 45.70 / 82.59 ms | 8.30 / 23.51 ms | 8 |

两页均能滚动至第 10,000 项，未一次创建 10,000 个可视卡片；两段滚动结束时 SQL 仍在运行。上述每次工作时间包含 Headless 截图读取，循环还额外等待 16 ms，因此**不转换成桌面 FPS，不据此宣称稳定 60 FPS**。原生桌面 GPU 合成和真实显示器帧时间没有测量。

## 内存

| 阶段 | 采样到的最大进程私有内存 |
| --- | ---: |
| 图标全部就绪 | 5,329.93 MiB，约 5.21 GiB |
| 配置页刷新并重新加载图标后 | 7,927.93 MiB，约 7.74 GiB |

250 ms 从后台采样进程 WorkingSet、PrivateMemory 和托管堆，原始记录全部保留。整个 UI 样本托管堆采样最大约 196.70 MiB；**仅看托管堆会漏掉位图等原生内存成本**。采样峰值可能漏掉更短的尖峰。

256 × 256 × 4 字节 × 10,000 张，单份解码像素约 2,500 MiB。两页各持有一份即可达到约 5,000 MiB，与本次结果量级一致。模组库静态字典按路径缓存解码结果，没有容量上限；配置页通过 `new Bitmap(path)` 单独解码，刷新又会创建新图像对象。这是已核对的代码行为；本轮没有强制 GC 后保留内存实验，**不能仅凭刷新后的增长判定永久内存泄漏**。

## 100 万条资源冲突扫描

复用现有冲突测试并补上 10,000 模组规模，每个模组一个合成补丁，资源总数 1,000,000，相邻模组共享 10% 资源；正文为空，Repository 为替身。它是单独的 TOC / 聚合基准，未与图片和 SQL 联合运行。每个规模只有首轮与重复轮各一次。

| 模组 × 每模组资源 | 首轮 / 重复扫描 | 重复轮缓存命中文件 | 重复轮累计分配 | 重复轮展示索引构建 |
| --- | --- | ---: | ---: | ---: |
| 1,000 × 1,000 | 813.1 / 632.3 ms | 1,000 | 278.7 MiB | 161.6 ms |
| 5,000 × 200 | 2,816.3 / 1,932.4 ms | 5,000 | 308.8 MiB | 201.4 ms |
| 10,000 × 100 | 4,993.6 / 4,967.2 ms | **0** | 419.7 MiB | 276.4 ms |

缓存当前上限为 8,192 个文件；10,000 文件按相同顺序全量扫描，会在访问后部旧缓存前不断淘汰它们，样本出现顺序扫描抖动。因此不能拿 5,000 模组的缓存收益承诺 10,000 模组重检也同样提速。没有为了这个结果直接增加缓存预算。

## 建议的小步优化顺序

1. 优先统一两页图片复用和生命周期，再让视口附近的图片优先加载；先降低已实测的多 GiB 解码成本。
2. 把同步的 SQLite / 目录及 sidecar 探测从 UI 线程移出，并合并一次加载中的重复工作。`Microsoft.Data.Sqlite` 的 async API 本身不会把查询变为后台 I/O；改线程时必须保留单连接的串行使用及取消清理。
3. 批量选择合并状态统计/集合通知；本次两页全选均出现约半秒停顿。
4. 单独评估 10,000 文件扫描缓存的命中策略，然后复测；不能用单纯扩大内存来抵消当前图片问题。

这些是基于当前证据的后续顺序，本轮没有混入行为改动或未经测量的性能收益。

## 补充：自动检查冲突的联合场景

补充场景在同一台机器和相同生产代码上运行，新增 10,000 个合成补丁，每个含 100 条资源，当前配置全部启用。相邻两模组共享其中 10 条，预期得到 50,000 组覆盖。补丁正文为空。相比上文原始带图场景，增加了资源文件且启用比例不同，不能直接把旧表当作开关对照。

为此，使用这套新数据分别跑自动检查关闭和开启组，每组启动独立测试进程，避免路径静态缓存累计影响内存。两组都有 10,000 张图片和持续 SQL 读写，执行相同搜索、排序、全选、刷新与两页各 180 次滚轮输入。开启组在初始化前保存自动检查设置，由实际设置加载触发调度；初次扫描完成后，两次通过配置页命令禁用再启用一个模组，分别在重检开始后滚动模组库和配置页。

扫描计时记录 `IsScanning` 的真实 false → true → false 变化，过滤重复属性通知；这里的管线耗时包括配置/模组读取、资源解析、结果整理和卡片回填，不等同于上文单独的解析基准。每次完成均检查 1,000,000 条资源、50,000 组覆盖、零读取警告及所有卡片角标；最后静置 5 秒检查没有额外自动扫描。另保留“扫描进行时”的输入探针和每次滚动截图工作时间。

**结论：这一联合负载下，开启自动检查冲突后不能保持持续流畅。** 关闭组也已有初始化与刷新长停顿；开启组扫描期间仍能响应输入并滚动到底，但出现明显抖动。以下是每组独立运行一次的本机观测，包含机器负载、GC 和缓存状态波动，不作为固定增幅或因果归属保证。

| 同数据操作 / 指标 | 自动检查关闭 | 自动检查开启 |
| --- | ---: | ---: |
| 主界面初始化 + 布局 | 36.00 秒 | 58.89 秒 |
| 初始化期间最长输入调度延迟 | 25.34 秒 | 36.70 秒 |
| 配置页刷新 + 布局 | 6.89 秒 | 22.07 秒 |
| 刷新期间最长输入调度延迟 | 6.89 秒 | 22.04 秒 |
| 模组库全选 / 清空选择 | 425.41 / 60.80 ms | 922.06 / 135.69 ms |
| 配置页全选 / 清空选择 | 666.36 / 511.61 ms | 1,310.28 / 1,076.99 ms |
| 图标全部就绪阶段最大私有内存 | 5,277.74 MiB | 5,468.64 MiB |
| 全场采样最大私有内存 | 7,897.98 MiB | 5,589.70 MiB |
| 全场采样最大托管堆 | 195.91 MiB | 415.88 MiB |

开启组运行更久，刷新后私有内存没有像关闭组一样升至约 7.71 GiB；没有改动图片实现，也没有强制 GC 或保留对象对照，**不能把这次较低的内存峰值解释为自动检查节省内存**。两组图标全部就绪时仍各需约 5 GiB 私有内存。

| 滚动场景，每组各 180 次 | 关闭：工作 P95 / 最大 | 开启：工作 P95 / 最大 | 关闭：输入 P95 / 最大 | 开启：输入 P95 / 最大 |
| --- | --- | --- | --- | --- |
| 模组库 | 34.29 / 76.76 ms | 107.70 / 438.63 ms | 4.36 / 33.04 ms | 31.79 / 166.18 ms |
| 配置页 | 43.05 / 98.24 ms | 157.84 / 212.50 ms | 8.18 / 52.97 ms | 36.96 / 150.02 ms |

开启组两页全部 180 次滚动样本都落在重检期间；两组最大实现容器均为 8，均到达第 10,000 项，两段结束时 SQL 都在持续运行。“工作”仍包含输入、布局与 Headless 截图，不换算为桌面 FPS。

| 自动扫描轮次 | 完整管线耗时 | 结果 |
| --- | ---: | --- |
| 启动后首次自动扫描 | 13.34 秒 | 100 万资源、50,000 组覆盖、零警告 |
| 启停模组后，模组库滚动期间重检 | 21.54 秒 | 同上 |
| 再次启停模组后，配置页滚动期间重检 | 21.82 秒 | 同上 |

开启组实际开始并完成 3 次，关闭组 0 次，静置期没有多余重扫。计时不含 750 ms 防抖。JSON 的 `initial_automatic_scan_ready`、`*_recheck_ready` 是其他操作完成后的剩余等待，不能当作完整扫描时间。

扫描状态开始或结束覆盖到的输入探针共 1,598 个，P95 **28.71 ms**、P99 **93.36 ms**、最大 **1,360.08 ms**；其中 34 个超过 50 ms，15 个超过 100 ms。该分布同时包含 SQL、图片和当时的 UI 操作，也不能替代全场初始化最长 **36.70 秒**、刷新最长 **22.04 秒**的停顿记录。

| SQL 联合负载，4 个独立连接 | 关闭 | 开启 |
| --- | ---: | ---: |
| 完成语句 / 写语句 | 1,025,093 / 51,258 | 1,163,959 / 58,201 |
| 压力持续时间 | 93.15 秒 | 171.60 秒 |
| 吞吐 | 11,005 条/秒 | 6,783 条/秒 |
| 各工作线程 P99 | 0.79～0.81 ms | 1.45～1.54 ms |
| 最长单语句 | 2,869.31 ms | 2,010.13 ms |

两组均没有 SQL 错误或锁超时。压力持续至 UI 流程结束，因此总条数与持续时间不同；吞吐是整段平均，不能解释为单独扫描阶段的吞吐。自动检查的补充结果进一步支持先处理图片成本、UI 同步读取和结果回填的建议；本轮只补测试与报告，没有修改生产逻辑。

- Release 解决方案构建通过，现有编译警告仍存在。
